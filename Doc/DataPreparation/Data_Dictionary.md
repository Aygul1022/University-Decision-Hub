\# University Decision Hub - Data Dictionary



\*\*Prepared by:\*\* Ümran

\*\*Version:\*\* 0.1 - Draft

\*\*Purpose:\*\* This document defines the meaning, required status, format, and examples of the data fields used in the University Decision Hub database.



\## Scope



This data dictionary covers the following tables:



1\. Faculty

2\. Department

3\. Course

4\. Instructor

5\. User

6\. CourseOffering

7\. OfferingInstructor

8\. Review



\## Status Note



This is a working draft. User and Instructor field decisions will be reviewed with Ozan. Database keys, constraints, and implementation details will be reviewed with Aygül.



\## 1. Faculty



The Faculty table stores the official faculty information. A faculty can contain zero or more departments.



| Field Name | Description | Example Value | Required? | Expected Format |

|---|---|---|---|---|

| FacultyId | Unique technical identifier for a faculty. It is generated by the database. | 1 | Yes, database-generated | Positive integer |

| FacultyName | Official name of the faculty. | Faculty of Engineering | Yes | Text, 2-150 characters |



\*\*Data preparation note:\*\* FacultyId will not be entered manually in the data file. We will prepare FacultyName, and the database will create the FacultyId during import.



\## 2. Department



The Department table stores academic departments. Each department belongs to exactly one faculty.



| Field Name | Description | Example Value | Required? | Expected Format |

|---|---|---|---|---|

| DepartmentId | Unique technical identifier for a department. It is generated by the database. | 1 | Yes, database-generated | Positive integer |

| FacultyId | Identifies the faculty that contains this department. This is a foreign key to Faculty. | 1 | Yes | Positive integer, must match an existing FacultyId |

| DepartmentCode | Short unique code used to identify the department. | COME | Yes | Uppercase text, 2-10 characters |

| DepartmentName | Official full name of the department. | Computer Engineering | Yes | Text, 2-150 characters |



\*\*Data preparation note:\*\* We will prepare the FacultyName, DepartmentCode, and DepartmentName values. During import, Aygül will match the faculty name with its generated FacultyId.





\## 3. Course



The Course table stores the permanent catalog information for a course. A course belongs to one department and can be offered in different academic years and semesters.



| Field Name | Description | Example Value | Required? | Expected Format |

|---|---|---|---|---|

| CourseId | Unique technical identifier for a course. It is generated by the database. | 1 | Yes, database-generated | Positive integer |

| DepartmentId | Identifies the department that owns the course. This is a foreign key to Department. | 1 | Yes | Positive integer, must match an existing DepartmentId |

| CourseNumber | Department-local course number. | 327 | Yes | Positive integer or approved course-code text |

| CourseName | Official name of the course. | Database Systems | Yes | Text, 2-200 characters |

| RecommendedStudyYear | The recommended student year for the course. | 3 | Yes | Integer from 1 to 4 |

| Credits | Local credit value of the course. | 3 | Yes | Non-negative integer |

| Ects | ECTS credit value of the course. | 5 | Yes | Non-negative integer |

| IsElective | Shows whether the course is elective. | false | Yes | Boolean: true or false |



\*\*Constraint note:\*\* The pair `(DepartmentId, CourseNumber)` must be unique. This means the same department cannot contain two courses with the same course number.



\*\*Data preparation note:\*\* We will prepare DepartmentCode, CourseNumber, CourseName, RecommendedStudyYear, Credits, Ects, and IsElective. During import, Aygül will convert DepartmentCode to the matching DepartmentId.





\## 4. Instructor



The Instructor table stores academic staff records. An instructor belongs to one department and can be assigned to one or more course offerings.



| Field Name | Description | Example Value | Required? | Expected Format |

|---|---|---|---|---|

| InstructorId | Unique technical identifier for an instructor. It is generated by the database. | 1 | Yes, database-generated | Positive integer |

| DepartmentId | Identifies the department of the instructor. This is a foreign key to Department. | 1 | Yes | Positive integer, must match an existing DepartmentId |

| FullName | Full official name of the instructor. | Dr. Ayşe Yılmaz | Yes | Text, 2-150 characters |

| AcademicTitle | Academic title of the instructor, if available. | Dr. | No | Text, 2-50 characters or null |



\*\*Design note:\*\* An Instructor record is separate from a User account. Creating an instructor record does not create login credentials.



\*\*Data preparation note:\*\* We will prepare DepartmentCode, FullName, and AcademicTitle. If the academic title is unknown, we will leave it blank and mark the source or note for later confirmation.



\*\*Review note:\*\* Ozan owns the detailed Instructor design. These fields should be confirmed with Ozan before the database schema is finalized.



\## 5. User



The User table stores registered application accounts. A user needs a department and study year before submitting a review.



| Field Name | Description | Example Value | Required? | Expected Format |

|---|---|---|---|---|

| UserId | Unique technical identifier for a user. It is generated by the database. | 1 | Yes, database-generated | Positive integer |

| FullName | Full name of the registered user. | Ali Kaya | Yes | Text, 2-150 characters |

| Email | Email address used for login and identification. | ali.kaya@example.com | Yes | Valid email format; unique |

| DepartmentId | Identifies the student's department. This is a foreign key to Department. | 1 | Required for reviewing | Positive integer, must match an existing DepartmentId |

| StudyYear | Current year of study of the student. | 3 | Required for reviewing | Integer from 1 to 4 |

| IsAdministrator | Shows whether the user has administrator permissions. | false | Yes | Boolean: true or false |

| PasswordHash | Secure hashed password value, managed by the authentication system. | \[system-generated] | Depends on authentication method | Never plaintext; not prepared in sample data |



\*\*Constraint note:\*\* Email must be unique. Two different User records cannot use the same email address.



\*\*Security note:\*\* Plaintext passwords must never be added to CSV files, GitHub, screenshots, reports, or the database.



\*\*Review note:\*\* Ozan owns the final User and authentication design. The final authentication fields must be confirmed with Ozan.



\## 6. CourseOffering



The CourseOffering table stores the period-specific opening of a course. It preserves historical information about when a course was offered.



| Field Name | Description | Example Value | Required? | Expected Format |

|---|---|---|---|---|

| OfferingId | Unique technical identifier for a course offering. It is generated by the database. | 1 | Yes, database-generated | Positive integer |

| CourseId | Identifies the course being offered. This is a foreign key to Course. | 1 | Yes | Positive integer, must match an existing CourseId |

| AcademicYear | Academic year in which the course is offered. | 2026-2027 | Yes | Text in `YYYY-YYYY` format |

| Semester | Semester in which the course is offered. | Fall | Yes | Approved value: `Fall` or `Spring` |

| Status | Current availability status of the offering. | Active | Yes | Approved value: `Active`, `Completed`, or `Cancelled` |



\*\*Design note:\*\* CourseOffering stores historical teaching periods. We do not overwrite an old offering when the same course is opened in a new year or semester.



\*\*Data preparation note:\*\* We will prepare DepartmentCode, CourseNumber, AcademicYear, Semester, and Status. During import, Aygül will match DepartmentCode and CourseNumber with the generated CourseId.



\*\*Open decision:\*\* The final uniqueness rule for CourseOffering and whether separate course sections are needed must be confirmed with Aygül before implementation.





\## 7. OfferingInstructor



The OfferingInstructor table connects instructors with the specific course offerings they teach. It supports one or more instructors teaching the same offering.



| Field Name | Description | Example Value | Required? | Expected Format |

|---|---|---|---|---|

| OfferingId | Identifies the course offering. This is a foreign key to CourseOffering. | 1 | Yes | Positive integer, must match an existing OfferingId |

| InstructorId | Identifies the instructor assigned to the offering. This is a foreign key to Instructor. | 1 | Yes | Positive integer, must match an existing InstructorId |



\*\*Key note:\*\* `(OfferingId, InstructorId)` is a composite primary key. The two fields together uniquely identify one teaching assignment.



\*\*Constraint note:\*\* The same instructor cannot be assigned to the same course offering more than once.



\*\*Data preparation note:\*\* We will prepare DepartmentCode, CourseNumber, AcademicYear, Semester, and InstructorFullName. During import, Aygül will identify the matching CourseOffering and Instructor records and create the OfferingId and InstructorId relationship.





\## 8. Review



The Review table stores a review written by a registered user about a course, its offering, and the assigned instructor selected by the user.



| Field Name | Description | Example Value | Required? | Expected Format |

|---|---|---|---|---|

| ReviewId | Unique technical identifier for a review. It is generated by the database. | 1 | Yes, database-generated | Positive integer |

| AuthorUserId | Identifies the user who wrote the review. This is a foreign key to User. | 1 | Yes | Positive integer, must match an existing UserId |

| CourseId | Identifies the reviewed course. This is a foreign key to Course. | 1 | Yes | Positive integer, must match an existing CourseId |

| OfferingId | Identifies the selected course offering. This is a foreign key to CourseOffering. | 1 | Yes | Positive integer, must match an existing OfferingId |

| InstructorId | Identifies the instructor selected for the review. | 1 | Yes | Positive integer; must be assigned to the selected offering |

| ReviewText | Main text written by the user. | The course was useful for learning database design. | Yes | Non-empty text; final length limit to be confirmed |

| CreatedAt | Date and time when the review was created. | 2026-10-23T14:30:00Z | Yes, system-generated | UTC date-time in ISO 8601 format |



\*\*Constraint note:\*\* `(AuthorUserId, CourseId)` must be unique. A user cannot create a second review for the same course.



\*\*Consistency note:\*\* The selected OfferingId must belong to the selected CourseId. The selected InstructorId must be assigned to the selected OfferingId through OfferingInstructor.



\*\*Data preparation note:\*\* Review records will not be collected from university catalog sources. They will be created later as approved sample or test data. Real students' personal information and real private reviews must not be placed in the sample data files.



\*\*Implementation note:\*\* Aygül will implement the database constraints that protect course/offering/instructor consistency. Ozan will prepare review-related tests and SQL queries.
