# Review submission contract and handoff

Status: implemented locally for Aygül's submission work. Proposed shared contract for Sami and Ozan; their agreement has not been obtained. No messages have been sent to teammates. No migration has been applied.

## Ownership

Aygül owns Review, ReviewCreateDto, ReviewCreatedDto (creation receipt), ReviewSubmissionService and POST /api/reviews. Sami owns authenticated GET list/detail/search and administrator-only PUT/DELETE in separate controllers. Those routes are not implemented here. Do not create a second Review entity or duplicate POST route.

## Request

```http
POST /api/reviews
Content-Type: application/json
```

```json
{
  "courseId": 1,
  "offeringId": 2,
  "instructorId": 3,
  "reviewText": "The exercises helped me understand the topics."
}
```

The DTO rejects unknown JSON properties, including userId, createdAt and administrator flags. Author identity is taken only from an authenticated identity's NameIdentifier claim. There must be one distinct positive integer subject identifying UserAccount.UserId. Claims from unauthenticated identities are ignored. No client header or query-string identity bypass exists.

## Stored record and receipt

ReviewId, UserId, CourseId, OfferingId, InstructorId, ReviewText, CreatedAt. CreatedAt is UTC, generated by the server. Leading/trailing whitespace is removed from the text; empty/whitespace-only text is rejected. Review text remains plain user content; future frontends must render it as text rather than HTML. There is no agreed text-size limit yet.

Successful POST returns 201 with these fields. No Location URL is emitted because Sami's detail route is not implemented yet. There are no draft/pending moderation states: persisted reviews are immediately eligible for authenticated retrieval. Author display name/visibility remains a decision for the reading DTOs; the creation receipt is not a public listing contract.

## Submission rules

1. Authenticated positive UserId must reference an existing account.
2. DepartmentId and StudyYear must be present and positive in the stored user profile.
3. Department must match the course's department.
4. StudyYear must be at least RecommendedStudyYear. Null or invalid course year blocks review creation.
5. OfferingId must belong to CourseId.
6. InstructorId must be assigned to that OfferingId. No additional same-department instructor restriction is imposed.
7. No existing review may have the same UserId and CourseId, regardless of offering/year/instructor.

Administrators have no eligibility bypass for submission. There is no attendance verification, email-domain check, prerequisite check, active-semester restriction or document verification.

## Responses

| Status | Meaning |
|---|---|
| 201 | Review saved; creation receipt returned |
| 400 | Invalid input or mismatched offering/assignment |
| 401 | Missing/unusable authenticated identity or account no longer exists |
| 403 | Incomplete profile, wrong department, insufficient year or course year unknown |
| 404 | Course does not exist |
| 409 | Duplicate review, changed reference or concurrent transaction conflict |

Failures use ProblemDetails; MVC malformed-input validation may use ValidationProblemDetails. Clients should depend on status codes, not exact error-message wording. On 409 reload before retrying. Cancellation flows through to database calls.

## Database integrity

- UNIQUE Reviews(UserId, CourseId), including concurrent submissions.
- FK Reviews.UserId -> UserAccounts.UserId.
- FK Reviews.CourseId -> Courses.CourseId.
- Composite FK Reviews(OfferingId, CourseId) -> CourseOfferings(OfferingId, CourseId).
- Composite FK Reviews(OfferingId, InstructorId) -> OfferingInstructors(OfferingId, InstructorId).
- All these relationships restrict deletion of referenced records.
- Eligibility reads and insert run in one serializable transaction. Serialization/deadlock conflicts produce 409; no automatic retry of the submission.

CourseId is controlled redundancy supporting course-level uniqueness, not strict third normal form. The composite FK prevents course/offering disagreement.

## Ozan integration dependency

A minimal shared UserAccount model is included because a real author FK and database-backed profile are required. It contains the previously agreed UserId, FullName, Email, nullable DepartmentId/StudyYear, and IsAdministrator. Email has a unique index; normalization/case-insensitive uniqueness and authentication storage remain Ozan's integration decisions. There are no account creation/login APIs, passwords, seeded users or token handlers here.

Ozan should extend/reuse this model, map trusted authenticated subjects to NameIdentifier/UserId, and configure authentication middleware. Never let public registration set IsAdministrator. Review eligibility uses stored profile values, not department/year claims that may become stale. Current anonymous requests return 401; valid submissions cannot be exercised through HTTP until authentication is integrated.
