## Stable identity on separate local databases

FacultyKey and InstructorKey are now persisted in nullable `ImportKey` columns on Faculties and Instructors. They are trimmed, uppercased and unique per table; both have a 100-character limit. Pre-existing records retain null keys. Local primary keys remain generated by PostgreSQL. DepartmentCode remains the department identifier.

This changes the earlier file-only-key design because names cannot safely identify instructors across repeat imports. Agree stable source keys with Umran and keep them unchanged between files. Two instructors with the same name can be separate people when their source keys differ. Do not invent a new key for the same person on each import. Keys are internal and are not added to public JSON responses.

## Import behavior

- New records are inserted in faculty, department and instructor order.
- Existing source keys with identical stored values are counted as unchanged.
- Department codes are compared ignoring case and outer whitespace; multiple local matches are rejected.
- A matching key/code with different names, title or parent relationship rejects the entire batch. This command does not update, transfer or delete existing records.
- A faculty name already present under another or absent key is rejected for manual review. An unkeyed instructor with the same name also requires manual identity review. Existing keys are never assigned by guessing from names.
- All writes share one serializable transaction. A conflict after early saves rolls the whole batch back. Database uniqueness prevents duplicate import keys. Concurrent operations may cause a conflict; rerun only after reviewing the cause.
- A connection failure during commit can leave the outcome uncertain. Inspect the database or rerun the same unchanged file; stable keys make repeats safe. Do not change keys to work around an error.

The command loads current catalog rows into memory and is intended for this project's small catalog, not a large streaming import. It accepts only localhost, 127.0.0.1 or ::1 with database name UniversityDecisionHub. Each teammate uses their own private connection settings. Anyone with local database credentials can run this developer command; it does not use web JWT roles.

## When ready to use it

First apply the approved `AddCatalogImportKeys` migration to your own local database. The importer refuses pending migrations and never applies them automatically. Rolling this migration back removes import keys and their history of identity; it is not a normal undo-import operation.

After that, from the repository root in PowerShell:

```powershell
$env:ASPNETCORE_ENVIRONMENT = 'Development'
$env:DOTNET_ENVIRONMENT = 'Development'
$catalogPath = (Resolve-Path 'Doc/Templates/catalog.example.json').Path
dotnet run --project Backend/UniversityDecisionHub.Api --no-launch-profile -- import-catalog "$catalogPath" --apply
```

The example inserts synthetic sample records into your local database. Use a reviewed private file instead for actual data. `--apply` is required because this command writes records; omit it and the command prints usage. Do not rerun the PostgreSQL initialization script.

Expected for the example in an otherwise empty catalog: 3 added and 0 unchanged. Repeating it unchanged should report 0 added and 3 unchanged. The first-import result was observed successfully. The repeat-import result is still an expectation, not an observed run.

Exit codes: 0 committed successfully; 1 usage, local-target or file-access problem; 2 invalid content, conflict or pending schema; 3 database operation failure. Error output avoids full records, passwords and raw database exception details.

## Learning the implementation

`CatalogImportCommand.cs` handles arguments, reads the JSON, checks the local target and schema, and prints the outcome. `CatalogImportService.cs` performs validation again as a service boundary, opens the transaction, maps source keys to local entities and saves each dependent level. Dictionaries are the in-memory lookup maps; ImportKey is what makes those identities survive after the command exits. Commit happens only after every level succeeds.

No users, login credentials, courses, offerings or assignments are loaded by this command. Their import formats remain separate work.
